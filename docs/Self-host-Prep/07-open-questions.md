# Phase 7 - Open Questions And Decisions Needed

Each item is phrased as a concrete decision with options and trade-offs.

## Decisions

| ID | Decision | Options | Trade-offs / Notes |
|---|---|---|---|
| OQ-01 | Self-hosted compiler source location | **Resolved: when the migration cutover begins, rename the current C# host compiler directory from `/src` to `/old_src`, then create a new `/src` for the Stark self-hosted compiler source.** | This keeps `/src` as the canonical compiler source location after migration while preserving the C# host in-tree for emergency recovery, comparison, and historical reference. Do not create a long-lived `src-stark/` tree. This decision only settles repository source placement; bootstrap staging, `build/` layout, and test layout remain separate decisions. |
| OQ-02 | Parser strategy T01 | **Resolved: keep `Stark.g4` as the canonical grammar reference and write a handwritten self-hosted parser.** Do not port the ANTLR runtime, generated parser, generated visitor, or generated parse-context object graph. | This keeps the grammar authoritative without committing Stark to generated ANTLR machinery. The handwritten parser should be recursive-descent/Pratt or equivalent, explicit, fast, and conformance-tested against `Stark.g4` and the host parser while the host exists. A Stark-native parser generator remains a possible post-bootstrap tool, not a self-hosting prerequisite. |
| OQ-03 | Resolve ANTLR version mismatch | **Resolved for self-hosting: no ANTLR runtime/generator is carried into the Stark compiler.** | The mismatch still matters only for maintaining the current C# host before retirement. `Stark.g4` is canonical; generated host files may be regenerated or frozen as a host-maintenance detail, but generated files are not source-of-truth for the self-hosted parser. |
| OQ-04 | Error propagation surface L01 | **Resolved: use leading `try` plus `from` funnels over structural `[Ok]`/`[Err]` enums.** Do not add `?`-style propagation. | `try` is visible and greppable, keeps early return explicit, and works with `System.Result<T,E>`, `System.Option<T>`, and user/domain enums that carry the same role attributes. |
| OQ-05 | Compiler invariant failure policy L07 | **Resolved: none of A/B/C — no trap/assert surface is added.** Invalid states are made unrepresentable instead: (1) restructure cross-pass lookups into typed handoffs, (2) exhaustive switches + definite-return analysis (STK3044/STK3045) turn impossible-state code into compile errors, (3) real environment failures are `Result` + `try`, (4) the small residual reports via `Result<T, InternalError>` to `main` or stderr + `System.Process.Exit(1)`. See doc `09` Error Model for the port convention. | A (trap APIs) was rejected as a give-up hatch contradicting "invalid states unrepresentable"; B alone is noisy; the resolution combines type-system guarantees with B for the residual. |
| OQ-06 | Optional/null replacement L11 | **Resolved: use `System.Option<T>` as the blessed convention.** C# nullable references, nullable returns, and `TryGet(... out T?)` port to `Option<T>` with `[Ok] Some(T)` / `[Err] None`. | Safe Stark has no nullable safe references; raw `null` remains only for raw pointers and FFI. Project-local option-shaped enums are still legal under the structural `[Ok]`/`[Err]` role model, but the self-hosted compiler should default to `System.Option<T>` unless a domain-specific enum carries clearer meaning. |
| OQ-07 | Compiler integer fact domain S05 | **Resolved: no public `BigInt`, and no arbitrary-precision requirement for self-hosting. Use a compiler-internal representation backed by Stark's fixed-width ceiling, `i1024`/`u1024`, for integer literals, range facts, enum tags, CTFE integer folding, SSA integer facts, and known-bit masks. Oversized literals or compile-time integer results outside that domain are compile-time diagnostics.** | This matches Stark's actual integer model, avoids importing a C# implementation detail into the language, keeps compiler numerics bounded and fast, and makes invalid oversized states explicit. |
| OQ-08 | Generic hashing/equality doctrine L06/S06 | **Resolved: combine A and C. Use generic `Hash` + `Eq`, `Ord`, and `Format` contracts as the blessed public language/stdlib model; use strongly typed compiler-internal interning for hot name/key paths.** Specialized compiler-only dictionaries are rejected except as temporary migration shims. See [19-generic-collections-and-interning.md](19-generic-collections-and-interning.md). | This benefits all users while still giving the self-hosted compiler fast symbol/name lookup. Text, path, and user-defined key types satisfy explicit contracts; compiler phases intern stable names at boundaries and then use distinct ID types such as `SymbolId`, `TypeId`, and `ModuleId`. Hash table iteration must not define package image, diagnostic, or golden output order. |
| OQ-09 | Package image format S14/T07 | **Resolved: use binary package images for normal compiler loading, with deterministic JSON/text inspection produced by `stark inspect-pkg`.** See [20-package-image-format.md](20-package-image-format.md). | This keeps the compiler hot path fast while preserving debuggability and diffable inspection output. Binary is the blessed dependency-load path. JSON/text are views for humans and tests, generated on demand from the binary image; build-time sidecars are deferred unless debug/test usage proves they are worth the extra surface. The current `.starkpkg.json` host artifact remains legacy/current-host format during migration, not the long-term self-hosted load path. |
| OQ-10 | TOML strategy S13/T04 | **Resolved: add a general reusable `System.Toml` parser/emitter and keep `Stark.toml`, `Stark.solution.toml`, and `Stark.user.toml` as TOML.** See [21-system-toml.md](21-system-toml.md). | This replaces the host's private `SimpleToml` with a real stdlib surface usable by the compiler, tests, tools, and users. Manifest schema validation remains a project-driver layer on top of parsed TOML values. Changing manifest format is rejected; a manifest-only parser is not the blessed long-term model. |
| OQ-11 | Build-driver concurrency L10/S16 | **Resolved: port the self-hosted build driver synchronously first; do not add `async`/`await`. If/when build or test execution is parallelized, use the narrow coordination surface in [22-threading-coordination.md](22-threading-coordination.md): explicit payload thread starts, `System.Threading.Synchronized<T>` / `Locked<T>`, and MPSC channels for progress/results.** | The host compiler's `async Task` usage is sequential I/O, so synchronous v1 is behaviorally equivalent. The chosen future parallelism path keeps Stark's existing threads/atomics, avoids a broad threading framework, and separates absolutely necessary coordination pieces from nice-to-have facilities such as thread pools, work stealing, `RwLock`, `Once`, semaphores, condition variables, thread locals, and async. |
| OQ-12 | LLVM integration T10 | **Resolved: use libLLVM as the primary backend integration through the LLVM C API. Textual LLVM remains only for debug, golden/artifact inspection, diagnostics, and stage comparison.** See [23-libllvm-integration.md](23-libllvm-integration.md). | This makes libLLVM part of the roadmap rather than a blocker to avoid. The selected implementation strategy starts with direct LLVM module construction through typed opaque handles, even for the first narrow backend slice; textual LLVM is printed from the in-memory module and is never parsed as a bootstrap bridge. Shelling out remains for final linking, native C compilation, SDK/toolchain discovery, and emergency diagnostics. |
| OQ-13 | Bootstrap policy T02 | **Resolved: keep it simple. Use the existing C# host compiler as Stage0 until the Stark compiler can build itself. Do not add a checked-in/downloaded blessed snapshot compiler artifact for self-host prep. Do not keep the C# host as permanent Stage0 after cutover.** | During migration: C# host builds Stage1; Stage1 builds Stage2; compare enough artifacts/tests to trust Stage2. After cutover, `/old_src` remains reference/emergency code, not the normal build path. Future releases can be built by the then-current Stark compiler like ordinary compiler releases; no separate snapshot provenance/rollback system is required for this three-person project. |
| OQ-14 | Stark test runner design TEST-01/T12 | **Resolved: generate an explicit `main` runner from `[Fact]` metadata.** No runtime reflection, no metadata walking at runtime. | The generator gives xUnit-like ergonomics while preserving Stark explicitness: discovered tests become ordinary generated calls to `System.Testing.RunFact` or its expanded runner APIs. Handwritten runners are allowed only as an early bootstrap fallback, not the blessed pattern. |
| OQ-15 | Test artifact access TEST-07 | **Resolved: use a fast typed in-process compiler test API as the blessed path; use a persistent/batched compiler runner with structured results for host and cross-stage tests; keep full CLI artifact export only for targeted golden/stage/debug tests.** | This preserves speed for large test suites, gives enough structured diagnostic/artifact access for deep pipeline tests, and keeps host/Stage1/Stage2 comparisons possible without spawning once per fact. Broad logs, timings, metrics, and machine-readable CLI output are not a general self-hosting requirement; add them only where a test or debug workflow needs them. This is a compiler/test tooling feature and must not change normal Stark user-program codegen or runtime execution speed. |
| OQ-16 | Memory model for compiler IR S17 | **Resolved: use arena/table storage with typed handle indices as the blessed compiler IR model, plus first-class extensible fact tables and fact-transfer verification.** See [24-ir-memory-and-fact-model.md](24-ir-memory-and-fact-model.md). | Owned trees remain acceptable for truly tree-shaped data, but MIR, SSA, artifacts, package imports, backend state, and cross references should use typed handles such as `MirValueId`, `SsaValueId`, `TypeId`, and `SymbolId`. Backend facts must not be comments or ad hoc metadata; they attach through typed fact tables with explicit lowering policies (`preserve`, `translate`, `consume`, `recompute`, `forbid-drop`, `debug-only`). Durable facts flow through package images; transient pass-local facts stay in compiler tables. `Rc`/`Arc` is not the default IR model for self-hosting. |
| OQ-17 | Alias/noalias proof model L13 | **Resolved: use explicit compile-time-only proof carriers for APIs that need alias facts; erase carriers before codegen; wrong proof use is a compile-time diagnostic.** External facts may be introduced only through a narrow `unsafe assume disjoint(...)` form with explicit root checks. | This combines the safety of compiler-checked alias proofs with a fenced escape hatch for FFI and externally-known disjointness. Backend validation may still assert invariants, but accepted Stark programs must not rely on LLVM catching aliasing mistakes. |
| OQ-18 | `build/` layout T05 | **Resolved: use option A. Formalize `build/<profile>/<target-triple>/<stage>/` with stable subdirectories for `bin`, `obj`, `pkg`, `stdlib`, `native`, `tests`, `diagnostics`, and `artifacts`.** See [25-build-artifact-layout.md](25-build-artifact-layout.md). | This keeps bootstrap outputs deterministic without adding an artifact database. `stage0` is the existing C# host compiler, `stage1` is the Stark compiler built by Stage0, and `stage2` is the Stark compiler built by Stage1. Project-specific ad hoc layouts are rejected because they make bootstrap, stdlib discovery, stage comparison, cleanup, and tests harder. |
| OQ-19 | Stdlib/package discovery T11 | **Resolved: use an explicit ordered discovery policy.** Resolution order is: 1. explicit override from CLI, manifest, or user config; 2. stage/build-local stdlib artifacts for bootstrap; 3. repo source or `stdlib/dist` artifacts for development; 4. installed bundled stdlib package next to the compiler distribution. If none resolve, emit a diagnostic listing every searched path. | This is the blessed approach. It keeps release builds clean-machine friendly, keeps contributors productive in source-tree development, lets bootstrap stages use their own `System` artifacts, and avoids hidden global or network discovery. Ordinary package dependencies should still come from explicit manifest/package references unless a future package manager decision adds another layer. |
| OQ-20 | VS Code/editor blocking status T13 | **Resolved: track editor/tooling updates, but do not block bootstrap on full editor parity. Update syntax highlighting/completions when source syntax changes land.** | This keeps the compiler work moving for a small team while avoiding stale user-facing syntax support. Deeper editor parity can trail self-hosting unless a feature is unusable without it. |
| OQ-21 | `comptime` scope L09 | **Resolved with schedule split: pre-self-host `comptime` is frozen at the current implemented baseline; broad CTFE plus program-structure branching is accepted direction but deferred until after bootstrap.** Structural facts remain compile-time-only and erase before backend lowering; this does not add runtime reflection. | This keeps existing constants, typed integer `comptime` generics, layout/table facts, supported finite/law CTFE, existing `System.Compiler` facts, diagnostics, and erasure available before self-hosting, while avoiding a full duplicate C#-host-shaped implementation as a bootstrap blocker. Broad evaluator parity, future fact expansion, and package/source preservation move to docs `26` and `27`. |
| OQ-22 | Traversal and comptime-generic scope L03/L05 | **Resolved: add three explicit `for ... in ...` traversal loop forms and typed `comptime` generic value parameters before self-hosting.** Traversal forms are borrowed element, mutable borrowed element, and indexed borrowed traversal. `comptime` generic parameters are Stark's const-generic spelling, e.g. `struct FixedBuffer<T, comptime u64[0 max] N>`. | This gives the compiler-port ergonomic traversal and reusable fixed-size abstractions without a general iterator protocol, `yield`, LINQ-style APIs, hidden iterator allocation, or hidden runtime dispatch. `comptime` is preferred over `const` because Stark `const` means deep interior immutability; here the meaning is compile-time specialization. |

## Unresolved Evidence Items

| Item | Why It Matters |
|---|---|
| Package compatibility details | **Resolved:** package images are compiler-version-local build artifacts during self-host prep. The binary header carries magic + exact format version, mismatches fail with a rebuild-packages diagnostic, bootstrap stages rebuild their own images, and stage comparison uses deterministic inspection/clean-build outputs rather than cross-version package-image compatibility. See [20-package-image-format.md](20-package-image-format.md). |

- `05-port-checklist.md` compiler target paths assume the resolved OQ-01
  migration layout: current `/src` moves to `/old_src`, and the self-hosted
  compiler owns the new `/src`.
- Roadmap milestones reference only gap IDs defined in `01-language-feature-gaps.md`, `02-stdlib-gaps.md`, `03-tooling-gaps.md`, and `04-test-infrastructure-audit.md`.
- Parser strategy is tracked as both L14 and T01 because it is a language-expression blocker for the compiler port and a tooling implementation decision. OQ-02 is resolved as handwritten parser + canonical `Stark.g4`; T01 remains open as implementation work.
